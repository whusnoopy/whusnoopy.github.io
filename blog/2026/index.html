下线 WordPress，躲过 PHP 漏洞，瘦身 Hugo 输出

2026年10月23日

八月底把博客迁移到 Hugo，九月初又把历史文章都按 Markdown 整理了一遍，之后正常写了几篇新文章。按迁移时的规划，把旧 WordPress 留在 VPS 上空跑一段时间，以备还有啥需要迁移的

这几天趁着 Tibo 不停重置 Codex 的使用额度，再让 AI 验证迁移确实没有遗漏，把旧系统下线并卸载依赖，顺便把之前模板在每个页面里完整输出的侧边栏做了下优化瘦身

下线旧 WordPress

从八月底切换到 Hugo 开始，访问就已经全部走 Hugo 生成的静态文件，nginx 配置里也没有再把请求转发给 PHP

这次让 AI 先帮忙核查了一遍，确认现在的文章、图片、RSS、搜索和评论标识都不需要 WordPress，旧站里的图片也都已经在新站找到对应文件，已有的文件和数据库备份继续保留，才开始动手

10 月 20 日先停掉 MySQL 和 PHP-FPM，释放空跑占用的 VPS 内存，禁用开机启动，顺带把之前人肉维护的每日备份到 Dropbox 和 Google Drive 的脚本也停了。同时让 AI 修了一个 RSS 的小问题，原来 /blog/feed/ 可以正常访问，但少了最后那个斜杠的 /blog/feed 会返回 404，现在加了跳转

停掉后又观察了一天，确认正常访问没受影响，21 日把 PHP、MySQL 相关的软件包卸载，再清掉旧 WordPress 目录和数据库文件，也省得每次 apt upgrade 还要更新一堆没用的包

非常巧，PHP 官方在 10 月 21 日发布紧急安全更新，修复两个可能导致未认证远程代码执行的严重漏洞（CVE-2026-109618 和 CVE-2026-109619）。我这边下午刚把 PHP 卸载完，当天就赶上了紧急补丁发布。八月底公开访问就已经不经过 PHP，这次连运行环境也收掉了，刚好省了追着看影响范围和打补丁的事，庆幸有时候抠门省事也能少操一点心

这也符合之前迁移到 Hugo 的目标之一，减少对 WordPress、PHP 等的依赖，只放静态文件在 VPS 上，未来再要迁移也容易很多

同步 whusnoopy.github.io

GitHub 很早就有这个用自己用户名开头、以 github.io 结尾的 GitHub Pages 托管服务，早先打算折腾 Hugo，也是从考虑 GitHub Pages 默认支持的 Jekyll 看起，后面发现还是用 Hugo 更符合自己的需求

这次顺带让 Codex 完成了对 whusnoopy.github.io 的镜像流程，未来如果懒得自己维护 VPS 了，再配好自定义域名和 DNS，把它改成主站应该也可以的

瘦身 Hugo 输出

往 github.io 做镜像同步时，发现 Hugo 的输出目录到了 600 MiB+，这个空间占用明显超出预期，原来的 WordPress 站点目录在清理前核查时约 264 MiB。Codex 在分析能否将 github.io 做镜像时还提到，GitHub Pages 已发布站点的大小不能超过 1 GB，这一下就用掉了大半

自己人肉简单看了下是不是附件图片什么的太大了，用 gdu 扫了下也还好，就是旧文章里的图片链接还在 wp-content/uploads，新文章的图片放在 media/posts 下。这些旧地址继续保留，毕竟二十多年的各种历史包袱，能不动就不动，省得哪天又冒出来一个旧链接打不开

继续看，是最终生成的各种 HTML 文件累积起来太大了，一开始还怀疑是 Tag 和分类太多，导致输出的文件数量过多，后来让 AI 一查，是每个页面重复输出了完整侧边栏导致的

迁移到 Hugo 时为了保留原来的使用习惯，把右侧按年、月展开的文章归档也搬了过来。这东西在 WordPress 时代用的是 Collapsing Archives，之前还为兼容 PHP 8 修过插件，自己用习惯了这一套，希望能继续按年月翻旧文章

不过之前本站的模板实现就是把二十多年的年月、八百多篇文章的标题和链接，以及折叠用的按钮、列表结构，全部生成到每一个页面里，哪怕后来加了默认收起来等 JS 行为，实际上每页光侧边栏就有大约 216 KiB 的 HTML

算上文章分类、标签、年月归档和各种分页，整站的两千多个页面，把这部分内容原封不动输出了两千多遍。难怪文章和图片都没怎么变化，生成出来的整站文件却有 600 MiB+

找到问题就改呗，现在虽然不用 WordPress 动态输出，但可以把侧边栏依赖的文章归档数据提取到一个共用的 archive-index.json，页面里只留容器，由浏览器读取数据来生成年月列表，展开某个月时再创建里面的文章链接。这样同一份数据不用在每个 HTML 里塞一份，也可以利用浏览器缓存，跨页面访问时不必每次都重新传输整份数据，原来按年月展开、记住展开状态的功能都还在

这一波整完，单页侧边栏从 216 KiB 降到 8.3 KiB，整站从 632 MiB 降到 141 MiB

后面继续把文章分类和常用标签也用类似的方式处理，两块共用一份 sidebar-index.json，再把分页模板输出里那些没必要的缩进和换行裁掉。最后结果是

构建状态 单页侧边栏大小 整站文件大小
优化前 约 216 KiB 约 632 MiB
年月归档改用共享 JSON 约 8.3 KiB 约 141 MiB
分类、标签及分页继续优化 约 1.9 KiB 约 125 MiB

后面的优化收益没那么大，不过现在整个输出约 125 MiB，已经比之前含 WP 系统的旧站目录小了，每次发布和同步 github.io 镜像需要处理的数据也少了很多，离 GitHub Pages 的容量上限也还远，满意

随记

八月底迁移时想着后面就安心写东西吧，结果这两个月又断断续续折腾了不少。现在旧系统退役，生成文件也瘦了一大圈，希望接下来能多写几篇文章，少折腾点博客本身吧

现在我也变成用 AI 来输出内容的懒人了，上面引用这部分是 AI 输出的原文，更前面的内容是让 AI 用我的文风出的草稿，我改了一遍后的结果。有好有坏吧，先保持自己的想法记录输出，再继续平衡内容中的机械味和活人感

交换 ThinkPad X1 Carbon Gen12 的 Fn 和左 Ctrl 键帽

2026年10月9日

用了快 20 年的 ThinkPad，一直习惯了 Fn 是在键盘最左下角，左 Ctrl 是在更靠近空格一侧，用左手小拇指卷起来压 Ctrl 已经成了肌肉记忆

不过联想在好几年前就允许在 BIOS 里交换这两个键实际的功能，让习惯 Ctrl 在最外面的人，也能用最外 Ctrl 而 Fn 在里面的布局

到了 ThinkPad X1 Carbon Gen12 (2024) 这一代，干脆物理键帽也是 Ctrl 在外了。虽然 BIOS 里能把键位逻辑改回之前的，但盲打按着和视觉上看着是反的，逼死强迫症

好在这一代也让这两个键的键帽尺寸一样，看起来应该是可以物理交换的，之前在 51nb 上也有人说换过，但都是说起来很容易的样子，没有更细节的实操过程，自己担心别手潮给掰断卡扣，反倒出事

最近搜到 https://support.lenovo.com/us/en/documentation/sg10846/Replaceable_keycap_(task)?language=en 有 X1C Gen14 官方替换键帽的详细图文教程，又找到 https://www.reddit.com/r/thinkpad/comments/1eb2ymr/swapped_fn_and_ctrl_key_physically_on_x1_carbon/ 这个帖，目测自己的 Gen12 跟 Gen14 是一样的结构，经过亲自验证，确定拆键帽的操作流程为

  1. 用塑料薄片（比如购物卡）从键帽靠屏幕一侧，分别撬两个角，小幅度抬起一点，听到咔哒声，会感受到卡扣脱离
  2. 手指拉起键帽翘起的一侧，往触摸板方向推一下滑出来

装回去时先从靠触摸板一侧斜着往屏幕方向推，把靠触摸板一侧的两个卡扣滑进去，然后沿平时打字手指往下按的方向，把靠屏幕一侧两个卡扣也摁上就行了

实际撬的时候，注意伸进去不要太深，大概就是我伸进去这个程度或更少一些，翘起来一边

撬开后是这样，注意我这里就是撬太深了，导致一开始把蓝色箭头处的剪刀脚结构中轴给撬了出来，还好把整个剪刀脚结构取下来能复原，然后再装回去的

修复 Fn 键下的剪刀脚结构后现在完美交换。全过程以联想官方那个 Gen14 的图文教程为准就好，虽然 Gen12 的官方手册里没有换键帽这个章节，但键帽结构实际是一样的。撬的时候用巧劲，别像我一开始撬板插太深进到剪刀脚下面还往上撬结果把剪刀脚中轴给拉出来

奥奥上小学了

作为二胎家长，对学校里各种要求更熟悉，没那么多新奇感，也没那么焦虑，一切都更淡定

奇怪的电子设备修理经历

2026年9月24日

最近“修”好了几台电子设备，给“修”字加引号，是因为其实也没有修这个动作，莫名其妙地坏，又莫名其妙的好了

红米 X65 电视 L65M5-RK 背光不亮

故障表现

这台电视机是 2021 年买了在家里客厅使用的，这个夏天的某一天，娃突然说屏幕没显示，仔细分辨后并不是机器彻底坏了或屏坏了，而是屏下背光不亮了。具体表现是开机后屏幕不亮，或闪一下，但是有声音，贴近看能看到非常暗的画面

排查定位

先用重启大法，长按开关和拔电源长按开关都试过，怎样都不行

上网搜各种表现，说大概率是背光坏了。打电话问官方售后，因为已经过保，且这个屏幕尺寸相对偏大，报价大几百，还不确定能弄好，这个价格就不如换个新的了。在 B 站上搜换背光的视频，还是有点麻烦的，主要就是要两人操作且小心点别把液晶面板给弄坏了

自己动手更换小米电视L65M5-AD背光，省了500块！教程！#小米电视#L65M5-AD#小米65寸电视 BV1U7421K7Am

最终决定还是给家里换个新电视，这个旧的弄来公司，如果能修好就给某个会议室用，修不好么就换铁盆吧

「维修」过程

在淘宝上按型号买好背光条，把家里之前用来拆集成吊顶的吸盘也带来公司，以备拆机时吸液晶面板用

某天中午吃过饭，拉上伞破一起开搞，期间引来一堆人路过围观「原来电视机里面是这样的呀！」「电视机还能修？」

在公司先确认故障表现还是一样的，各种哼哧哼哧拆，螺丝真的多，而且还有好几处是隐藏的，要拆掉前面部分才能露出来

面板拆下来时发现是用胶粘在框上的，看起来跟之前办公室那批面板脱落的 Dell P2418D 显示器一样，难怪现在大部分电视机都说不允许吊装时倾斜向下

最后拆到背光后那层导光纸时，原来是粘上去的，贼难揭下来，中间还撕破了一点

在最后准备换背光条时，还插电验证了一下，还是原来的问题表现，背光闪一下就不亮了。等真正看从哪根开始换时，随口说要不再通电看下？于是插电按了一次开关，亮瞎狗眼的整片背光亮起来，好了！

各种验证，背光的确是好了，就这样莫名其妙也不知道动了哪里，如果是接触不良啥的，那凭什么拆的过程和准备换之前的第一次验证又不行

然后就是继续哼哧哼哧装回去，过程中继续验证面板没被整坏，期间有出现过面板左右两边亮度不一样的情况，估计是走的不同的排线没插好，重新插拔面板排线后没再出现这个情况。后来还发现面板周围那圈胶估计不太牢了，就用宽的打包胶带给四周贴了下，挂到一个电视推车架上，留在公司会议室里给充公吧

后面几天持续验证，确认不是一时的回光返照，而是真的持续可用，但家里新电视都买了，也懒得再拖回去，至于已经到货的背光条，问过淘宝商家说不影响二次销售可以无理由退货，那就退了吧

ThinkPad X1 Carbon Gen6 屏幕无显示

故障表现

这台 X1C2018 笔记本是从闲鱼收的，给娃拿来学编程用，大致配置是 i7-8650U / 16G / 256G / 2560x1440 高分屏 / LTE。机器是好机器，也是一代经典，之前还有一台 i5 处理器 1080p 屏幕的给老爸用了

先是在家偶尔遇到使用过程中屏幕黑掉，调整一下屏幕开合角度可能就会恢复，后面是在带去上课的时候遇到黑屏，开合屏幕也无法自愈，但是关机回家放了半天就好了

再就是月初某次去上课，黑了就再没点亮

排查定位

电脑能开机，外接显示器可用，说明主板啥的都没坏。进到系统里还能看到有内屏，并且分辨率啥的信息都正确，说明至少主板上的显卡部分都是好的，面板大概率也没坏

拆机，插拔各种排线，试图排除接触不良的情况，无果

找 ChatGPT 问，说大概率是屏线坏了，或者是屏线靠面板侧的接触有问题。搜对应的 Hardware Maintenance Manual，看起来自己也能拆，后面又找了视频看，拆到面板这一层还是能自己搞定的

ThinkPad X1 Carbon 6th更换天马2K 120hz屏幕，详细教程 BV1B94y1x7To

「维修」过程

吸取了上次修电视机背光的经验，这次在没有百分百确定故障原因前先别着急下单买屏线

拆到屏幕侧，重新插拔屏线在面板侧的接口，还是不行

期间伞破拿他的同款 X1Cg6 来，说看看能不能直接上 2K 屏，行的话回头他整个 2K120Hz 的天马屏看（就是上面 B 站视频里那个），换到他那，也是点不亮，但系统能读到屏幕信息

好了，各种排除法，我的电脑其他部位没问题，这个屏带线插到另一台电脑上故障表现一样，去淘宝下单屏线准备再抢救下呗

把裸面板加屏线接回自己电脑，准备移到空工位放着等淘宝屏线到货再说。鬼使神差又按了下电源键，突然发现屏幕上红底的 Lenovo 标志出来了……

对，就是这样又好了，后面任我各种晃悠屏线都没问题，换到伞破电脑上试过也没问题，再继续装回来，跟淘宝商家商量还没发货可以退单的吧，倒是屏幕的 B 面是粘上去的，另外下单胶带来弄

后面自己用胶把 B 面粘回去，有点偏差，而且把摄像头遮挡滑盖的黑阀拨片给卡住了，不过倒是问题不大，继续用吧

ThinkBook 14+ 2022 无法开机

故障表现

某台被当测试机用的 ThinkBook 14+ 2022，i5-12500H 款，正式的型号应该叫 ThinkBook 14 G4+ IAP 21CX

某天被同事反馈开不了机，过去看不管是否插外接电源，按开机键要么没反应，要么键盘背光灯亮几秒，但屏幕没显示，也没听到系统风扇转，然后就完全掉电

此处注意到插外接电源时，机身侧面 USB-C 口旁边的电源指示灯，是黄色闪烁状态，这不符合官方说明里只有白色或黄色常亮或熄灭的状态，看起来整个电源系统都可能有问题

排查定位

既然插电有问题，那先换个电源看？不行。用不同电源插不同的 USB-C 口？也不行。拔电只用电池呢？还是不行

最近这些年的 ThinkPad 和 ThinkBook 都有 EC 重置孔，之前遇到 USB-C 口不能用，几乎都通过重置 EC 的方法解决。那戳 EC 孔 20 秒，再试，依旧不行。除了戳 EC 孔重置，也长按电源键释放可能的残电？不出意外并没有任何反应

拆机，断掉电池和主板的排线，只接外部电源呢？故障表现一模一样

想断掉主板 BIOS 电池，但这个在主板副板的背面，要挑开那个排线得把主板副板整个取下来，觉得太费劲就没在这一段来做这个尝试

最小化主板，把 SSD、无线网卡、屏幕排线、散热风扇、主板副板 这些能从主板上断开的通通断开，用机器原配电源和另一个 ThinkPad 原配电源在两个 USB-C 口交替尝试，依旧是插电闪黄灯

「维修」过程

外接键盘映射苹果 Globe/Fn 键

2026年9月1日

曾经在 macOS 实用小工具记录 2 里提到苹果修改了锁屏快捷键，可以用 Ctrl+Cmd+Q 锁屏，而不用模拟之前的 Power 键，对 Karabiner 不再有需求，结果最近还是装了回来

macOS 26 开始的全屏快捷键变化

在 macOS 26 Tahoe 之前，对应用全屏（新建占据整个桌面）的快捷键是 Ctrl+Cmd+F，这个在外接键盘上也能直接按出来，但后面改成了 Globe+F，这个 Globe 键就是苹果笔记本电脑或原装外置键盘上原来的 fn 键，上面有个小地球图标的，俗称地球键

这下好了，要全屏要么点窗口左上角的红绿灯按钮，要么用苹果笔记本机身键盘上的 Globe+F 的快捷键，在外接键盘上都无法使用

在外接键盘上切换全屏的尝试

macOS 系统设置里改快捷键

这个方式是说在 macOS 的系统设置里，增加一个「切换全屏」或「Enter Full Screen」的快捷键，然后映射成自己想要的键

我自己试过一下，不是那么灵光，也不太好用，放弃

使用第三方窗口管理工具如 Rectangle

Rectangle 是我近年来替换 Spectangle 后的窗口管理工具，本来随着新版本 macOS 把左半屏、右半屏、最大化等几个操作支持后，连这个工具都可以不用，但偏偏 macOS 原生的都是 Ctrl+Globe+Left、Ctrl+Globe+Right、Ctrl+Globe+F，都还是无法在外接键盘上使用的

等为了在外接键盘上更方便使用窗口布局且不用去改系统快捷键，把 Rectangle 装回来后，发现 Rectangle 无法支持系统级的全屏操作，所以这条路也走不通

使用 QMK/VIA 改键位映射

我现在在办公室使用的 Keychron K8P 支持 QMK/VIA，那么去 usevia.app 可以快速改键映射

但是苹果这里又搞事情，原生的 Globe 键并没有相关键位码，网络上找到的方法要么是通过 QMK 改固件，要么说的用 Any 键传入 0x2100 但现在也不生效，至少没法起到 Globe 键的作用

使用 Karabiner-elements 改键位映射

参照 https://github.com/the-via/releases/issues/92#issuecomment-3805418968 这个 VIA 项目里 Issue 的讨论，最后还是用 Karabiner Elements 解决问题

我把自己 K8P 的截屏快捷键先改成 F24（默认行为是发送 Cmd+Shift+4 调用系统截屏快捷键），然后再到 Karabiner Elements 里把 F24 映射成 fn (globe)，现在尝试按 F24+F，可以在支持的应用里切换全屏

现在就是这个键并不在右手小拇指周边，不是太方便，本来考虑把 Fn+L_Option 改成 F24 来达到映射，后来发现不行，因为按下 Fn 后，原来 F 键的逻辑也变了，这时候键盘工作在第二层键位上，而 F 键默认是在改键盘灯光 RGB 的参数

剩余对当前 macOS 里全屏快捷键的吐槽

之前 Ctrl+Cmd+F 的快捷键用的好好的，偏偏要改一个外接键盘无法支持的 globe+F，而且原来的快捷键几乎所有的应用都支持，改的这个好多应用又不响应，比如 VSCode 就不行，Ghostty 也不行

多年前让苹果成为开发者友好的设备，据说是 @dhh 及 Ruby on Rails 这帮人推动，现在 dhh 也对目前 macOS 的状态不满，在推动 Omarchy 项目，看看会不会三十年河东三十年河西，回头 Linux 变成开发者更友好的环境

同一网页引入两个不同版本jQuery引发的问题

2026年4月8日

昨天在前端工程遇到一个以前没有想到过的问题

在维护了十多年的主项目上，最近完成了把 Knockout.js 从用户侧前端子工程 acorn 完全移除的工作，原来的要么迁移成 React 实现，要么把自家运营运维侧的工作移到 staff 子工程。在 staff 子工程里目前还有 Knockout.js 的前端页面逻辑和组件，以及一些以前仿照 bootstrap 写的样式和 js 组件，以及基于 jQuery 的日期选择器 datepicker 和时间选择器 timepicker

但昨天发现某个页面一个封了 datepicker 的 input，通过 data-bind=“textInput” 跟 knockout.js 绑定有奇怪的行为。鼠标点选，input 输入框内文本改变，用 $(el).val() 取的值也正常，但 ko 绑定的值不变。如果直接在 input 框里输入，ko 绑定的值就能正常更新

直接 input 输入可以改变 ko 绑定值，说明 ko 绑定没出问题，鼠标点选后 ko 绑定值不变，说明监听机制哪里有问题。因为这一波迁移里把原来多个版本混用的 ko 统一到了 3.x，先查是不是 ko 跨版本有监听事件的变化，ko 官网没说，某 AI 说 ko 3.x 开始还是现代浏览器有啥啥啥事件不再绑定，但尝试手工验证， $(el).trigger("input") 和 $(element).trigger("change") 这些明确说应该有效的，也不能让 ko.observable 的值更新

自己看业务代码和 datepicker 的代码（都是十年前自己写的），git 记录都显示没变啊，调试过程该有的事件都正常触发。把问题代码涉及的链路和表现丢给 Codex GPT-5.4 xhigh，一开始还说需要检查 ko 绑定机制和 vm 初始化顺序，但这些跟之前正常工作时都没变化。后面揪出来在 jinja2 模板层，渲染 HTML 时引入了两次不同版本的 jQuery，在 ko 绑定时用的第一版，后续 datepicker 初始化时关联到第二版，两边 $.event 不通？两套 jQuery 各自维护了自己的事件缓存和 handler 列表，所以 datepicker 库通过第二套 jQuery 发出的事件到不了 ko 在第一套 jQuery 上注册的 handler，而人肉改 input 里的内容走的浏览器原生 DOM 事件，ko 用的那一版 jQuery 有正常监听能生效。最终移除没必要多引入了一次的 jQuery 后，确保 Knockout.js 和 datepicker 使用的是同一版 jQuery 后恢复正常

前端这些诡异的大坑啊，以前为了弥补浏览器能力不足而需要 jQuery 去封装的各种基础能力，现代浏览器都原生支持（主要是选择器和事件触发监听），未来能走原生都走原生吧

断电长按电源键可解决绝大部分USB-C/雷电口设备问题

2026年3月31日

个人和公司都遇到过笔记本电脑或显示器或别的设备的 USB-C 或雷电口，不能充电、传输信号等问题，大部分情况下，断电后长按电源键做重置就可以解决绝大部分问题

  • 断电

    • 笔记本电脑需要拔外接电源，最好在 BIOS 里断掉内置电池供电，取下一切连在笔记本电脑上的外设，包括但不限于 U 盘、无线鼠标接收器、网线等
    • 显示器拔掉电源线，最好也把所有数据线也拔掉

  • 长按电源键

    • 笔记本电脑在 BIOS 断内置电池的情况下长按电源键不会开机，保持按下 10 秒以上，最好 15 秒或 20 秒。如果没有 BIOS 断内置电池的机型，大概率长按下会先开机，再自动关机，不管他一样按够时间
    • 显示器就是长按电源键，按够时间

  • 恢复

    • 笔记本电脑插外接电源适配器，正常开机就行
    • 显示器插好电源线和数据线，正常开机就行

原理：设备的 USB-C 控制器或雷电控制器进入了奇怪的工作状态，断电长按电源键是让其恢复默认状态，就是重置
